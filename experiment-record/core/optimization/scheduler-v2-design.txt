Read-only scheduler V2 design review — no code proposal, build or game launched.

Disposition: technically reasonable as one narrowly isolated experiment, not justified for adoption and not a priority solely on V1's ~1% partial/flat CPU signal. Finish V1's broader evidence first. If sparse admissions are common and unrestricted/high-participant workloads matter, V2 tests a distinct source of needless fanout: submit currently broadcasts even for one admitted job. With the affinity ceiling and dense batches, opportunities may be small. Do not project oversubscribed auto32 benefits onto preferred small counts.

Shape (conceptual only): a mutex-held deferred-ready helper accepts a conservative upper bound on newly eligible jobs. Zero/zero-worker => no notification. If presentation or presentationPending exists, retain the original broadcast. Otherwise cap the budget by actual workers.size(); if the budget reaches that worker count, use one broadcast; for smaller budgets signal at most that many workers individually. Call with slot.total at successful admission and1 at lane completion/continuation requeue. Leave run/service/presentation/stop and join-CV notifications unchanged. The actual-worker bound avoids O(group.count) notification loops and uses real scheduler capacity, not a hardware/clock heuristic. A job count is an eligibility upper bound: serialized lanes can make fewer jobs ready.

Lock obligation: submit currently unlocks at the end THEN ready.notify_all(). Calling a helper that reads presentation pointers after that unlock races with worker presentation completion. Perform the decision/notifications immediately BEFORE lock.unlock(), after all slot state, sequence numbers and counters are installed. completeJob/settle already run under mutex. Notifications under the mutex may wake threads that briefly contend for that mutex; the owner releases immediately afterwards. Do not add expensive claimable-job scans, wake counters, idle-worker registries or timing logic merely to refine the bound.

Required-work correctness:
- Admission's total is >= number of jobs newly eligible in that slot. A lane predecessor's completion can make <=1 next ordinal eligible. A resumed continuation requeues one existing ordinal.
- Every worker can claim deferred jobs; without any active/pending presentation, claim(false) precedes optional WorkerOnly processing. A worker already inside optional work isn't a CV waiter. With presentation present, preserve all-wake because the designated worker may choose its fairness chunk before claiming required work.
- A presentation admission after the helper decision performs its own retained broadcast. State transition, CV predicate and claim arbitration retain the same mutex; work persists in slot state if nobody is sleeping.
- CV waiters are not permitted to sleep while their predicate is true at wait entry. HOWEVER do not assume seen==generation for all sleeping workers at every instant: run changes generation under mutex then broadcasts after unlock. External admission/resume may interleave in that gap and wake a stale-generation waiter, which invokes run first. Progress still relies on run's retained broadcast and loop predicate checks. Add that interleaving to gates.
- Slot/run/presentation completion CVs stay separate and broadcast; changing them to single wake could strand a waiter with a different predicate.
- No change to due ordering, lane admission, source/RNG/state, publication deadlines, exceptions, owner serial fallback or external ticket lifetime.

Generalization/cost risks:
- k notify_one operations can cost more than one notify_all. The actual-worker-count broadcast branch avoids repeated signals when enough admitted jobs could use every worker, but medium-k cases can still regress. Under-mutex repeated signals can increase lock reacquisition contention.
- A conservative total overstates eligibility for serial lanes, so V2 does not eliminate every unnecessary wake. Counting exact ready work would add scans and state complexity; reject that expansion unless measured necessary.
- Generic WorkerOnly idle opportunities can change when single-job admissions repeatedly wake the designated worker, which is excluded from maintenance. Condition variables promise no waiter fairness. Retaining registration broadcasts doesn't prove every future optional pass runs. Do not call this behavior identical or weaken any required device lifetime/terminal-proof guard.
- Actual current production BackendSession explicitly has NO learned profiles/observations. Map::configureCompute and clear set externalInitialization=true; GradientDeviceService's dedicated broker initializes the accelerator. Generic executor comments mentioning idle observations should not be presented as current learned GPU training. Live GPU initialization/cancellation/quarantine/commits remain gates because changing CPU wake service latency can affect backend timing even though initialization ownership is unchanged.

Focused test extensions, before any release experiment:
1. Cold idle pool, no presentation/service: submit1job, then2independent jobs whose callbacks synchronize at an entry gate. For N>=3 participants, both jobs must enter before the gate releases; one notification for total2 is insufficient. Repeat for total<workers, total==workers and total>workers; zero-count groups, separate serialized lane groups and mixed lane/NoLane admissions. Assert complete counts/order/lifetime, not a particular condition-variable waiter.
2. Keep V1's external-resume tests: two suspended lanes/nonzero index, designated worker deliberately held in presentation, or a normal worker held in WorkerOnly with no presentation. Resolve from an external producer and complete required joins BEFORE releasing optional gates, without fresh admissions/run broadcasts after resolution. Test duplicate/early/failing resolutions and retained tickets after shutdown.
3. Add sparse admissions while presentation is pending/running and with a continuous required backlog; preserve the spare-worker required-progress and designated-worker fairness tests. Existing one-worker behavior (one chunk can delay joins) stays valid. Pending fairness cannot be forced by public APIs to choose an exact sleeper; combine source invariant with repeated bounded stress, don't claim exhaustive schedules.
4. Concurrent blocking run generation and externally settled deferred tickets: gate only some run callbacks and require a spare worker to settle continuations/lanes, then safely release/join. Cover the run state-update/notify gap without changing run notification semantics. Include reconfigure/shutdown/creation-failure and N1/N2/N3/several/many participants.
5. Generic service eventual-opportunity probe: register a bounded service, then offer sparse independent required jobs, record service opportunities/worker roles and hold/release paths. An indefinite optional pending tail may be allowed by current API; document rather than silently interpreting a required checksum pass as preserved optional servicing. All cleanup gates must quiesce callbacks before stack references die.

Existing current3 browser verification (27 cases/6 corpora/188C++ each) DOES NOT cover unbuilt V2 or candidate4. Apply whole executor corpus and new focused tests to each actual candidate, then native/wire/save/replay and available browser/native scheduling boundaries. Compare original/V1/V2 as isolated factors on sparse and dense map/AI workloads, explicit small/many participants and GPUon/off, with exact traces and device health. Wall/CPU/sysCPU/context switches are separate; no universal speedup from a microbenchmark or one oversubscribed stratum. Root may reasonably reject further V2 work if completed V1/general workload evidence makes its cost unjustified.
