Replay reserve semantics and representation review
Read-only audit; no game/build launches. Source references below are one-based in replay-reserve/source/src/replay/ReplayTelemetry.cpp (prototype), with unchanged implementation regions traceable to original frozen source.

Exact count and order
capture:89–104 computes K = count(v.valid for f in [0,min(fields.size,current.values.size))) + named.size. The existing append loop uses exactly the same bound/valid predicate; all named entries follow it unconditionally, in existing vector order. reserve does not insert, erase, sort, normalize, format, or mutate values. Available=false rows skip both reserve and all inserts; inactive records still skip capture. Empty K calls reserve(0), which does not allocate for fresh row.values. Different schema/current lengths still truncate at the existing minimum. Invalid numeric entries still disappear; invalid/nonfinite real display still becomes the same “Unavailable” text via display:34–46. Named entries have no validity flag, so all are counted/copied. Duplicates or malformed names stay duplicated/unmodified; no new producer validation is introduced.
Schema replacement/new fields simply changes K on a newly constructed row at the next capture. Every schema field includes its existing updated timestamp; textual values/metadata are unchanged. Row operator== (ReplayTelemetry.h:14) compares contents and ignores vector capacity, so change-frame decisions remain identical. Team iteration, record iteration, latest map-key insertion/overwrite, frame changes and deleted-controller marker order remain identical (capture:76–116). Disappeared-controller copies and values.clear remain unchanged, including any retained capacity on those markers.

Ownership/concurrency
AI.cpp:241–249 copies completed worker telemetry into the owner series; AI.cpp:481–493 samples only published output for async controllers. Capture does not visit worker-owned decision state. The counting pass reads published validity flags before the unchanged construction pass. Under the existing owner-phase contract they are stable. This patch introduces no concurrency/atomic boundary. If a caller concurrently mutates the same Series, its preexisting unsynchronized construction is already invalid; do not treat an unstable count as a legitimate schema update mode. Even a different count would affect capacity, not the append-loop semantics, but this does not make data races acceptable.

Repeated captures, truncation, frame cap
capture:69 returns immediately after truncation; present/until updates remain identical. Fresh local row/latest/frame objects are created per capture, so no capacity persists between row constructions except rows retained in history and their unchanged copies into latest/current. Unchanged content produces no new frame (118–119), exactly as before. The reserve can save intermediate growth even for a row later found unchanged, but that benefit is unmeasured. Logical cost uses the same32per row and24per value plus lengths (120–126), same remaining16MiB and65536frames check (127), same until=step-1 on rejection, and same current replacement/frame push (133–135). Extra allocation can happen before this existing budget check, as could old growth. A rejected tentative row still frees its local allocations. No capture cadence or truncation policy changed. Fixed logical budget is not an actual heap ceiling.

Overflow/resource failure
Loaded ordinary telemetry is constrained to fields<=4096 and named<=132; presentation telemetry has fields==0,named<=4228 (AITelemetry.cpp:245–302, AITelemetry.h:22–23). Thus accepted loaded K<=4228, independent of host width, with no count overflow. Native producers are not newly validated by this patch. For well-formed live std::vectors with this ABI, element max_size bounds make size_t addition safe: each NamedValue has four strings+Uint32; each Field three strings+enums, so the sum of their theoretical maximum element counts is far below SIZE_MAX. If K exceeds destination vector.max_size, reserve throws length_error earlier than old insertion eventually would; if the allocator is exhausted, allocation failure timing can differ. This is allocation-strategy equivalence under successful allocation, not identical exception points under artificial OOM. Malformed memory/vector internals are outside C++ object invariants. Existing cost/text-size overflow and writer narrowing are untouched; changing their admission checks would be a separate compatibility task.

File/feature preservation
write:164–189 still emits AIT1 magic0x41495431, version1, until, truncated, frames, ordered rows and all four strings+updated fields, with exactly the old calls. read:191–245 and apply:247–279 unchanged. capture fields are presentation-only; no gameplay read added. No header/ABI, numeric formatting, historical metadata, replay acceptance, AI telemetry schema or simulation version gate changed. Optional capacity stdout is separate from OutputStream and gated env1; windows disable it. Exact original/protooff/protoon replay bytes plus complete per-tick GCS are required by root before timing; source reasoning is not a substitute. This audit covers Linux release source; no cross-platform games have been run for the prototype.

What may be estimated before diagnostic results
Peak raw stack shows46,235,648bytes attributed to capture, plus other capture allocations; it does not identify precise inlined allocation subtype. On the expected LP64 C++11 libstdc++ ABI, four32byte strings+Uint32+alignment predict sizeof(NamedValue)=136. IF that entire stack is the value vector backing allocation,46,235,648/136=339,968 retained capacity slots. This is a conditional arithmetic estimate, NOT a measured slot count or verified allocation subtype. Actual fields-per-row, sum capacities, truncation tick and sizeof values remain pending diagnostic output. Do not derive live value count from allocation-call totals; those count all intermediate growth and discarded snapshots. Source libstdc++13 bits/vector.tcc:68–86 allocates exactly n on fresh reserve, while C++ portability only guarantees capacity>=n. Pending diag directly measures size/capacity/sizeof on the target runtime. Text capacities include SSO and cannot be summed as external heap bytes. Value vector object storage is capacity*sizeof(NamedValue); external string blocks, vector allocator overhead, frame/row objects, current map and transient latest copies are separate.

Next feature-preserving options (rationale only; not built)
1. Lower-risk same-TU reader reserves: after validated counts, reserve frames(count), frame.changes(rows), row.values(fields) in read. This preserves successful decoding, field order and accepted bounds, reducing replay playback growth/slack. It does not address writer/capture heap and must check error timing and malformed inputs; do not conflate its projected benefit with current headless benchmark.
2. Shared immutable metadata in Stream-private representation: intern repeated name/unit/meaning text by exact bytes, scoped to the Stream, with stable lifetime across all retained frames. Keep value text and updated timestamp per sample; preserve duplicate entries/order and metadata changes/schema generations by content IDs, never assume names identify unique fields. On write, materialize exactly the existing AIT1 strings in the same sequence. On read/apply, preserve legacy bounds and materialize complete NamedValues where public API requires them. This needs a private representation/header change and focused replay/seek/save lifetime tests; avoid process-global unbounded interning. Benefit depends on measured metadata repetition/external string sizes, not fourstring sizeof alone.
3. Store retained complete frames/rows in compact serialized internal buffers while maintaining only current owner comparison rows: retain exactly the same AIT1 payload information, preserve logical budget and truncation decisions, and emit the same bytes/header. For generic OutputStream backends, decoding/re-emitting primitive calls may be needed; do not assume raw binary copying preserves other backends. Store/update offsets and row boundaries for apply/seek. This can bound history closer to actual wire payload while keeping all metadata/values, but requires broader implementation/compatibility checks and measured CPU/decode cost. It is a promising representation direction, not a low-risk follow-up patch yet.
4. Capture-time transient/current duplication: latest[row.player]=row copies the complete row, then frame.changes moves the original (106–108). Current map retains the latest comparison data independently of history, necessary for unchanged-frame decisions. A shared immutable row representation could remove duplicate text/object ownership without changing comparisons. Simply moving row into latest before frame recording would empty the frame and DROP data; never do that. Reuse/arena strategies must keep old frame ownership immutable and all controller transitions intact.
5. Actual memory accounting as telemetry only: add actual retained capacity/object/text metrics or a diagnostic ceiling assertion without changing truncation policy. Changing the16MiB budget calculation to sizeof/capacity would truncate history earlier and therefore remove retained telemetry; that violates the current strict feature/format preservation target unless separately authorized. Do not propose it as a free optimization.

No reserve impact, exact capacity saving or next representation speedup claimed before queued measurements. Current prototype does not reduce metadata/value object count; it targets excess capacity and growth only. Preserve every telemetry feature.
