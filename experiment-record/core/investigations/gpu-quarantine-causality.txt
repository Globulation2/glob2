Causal source mechanism (current latest/frozen source)
1. GradientPipeline.h:204–208: ANY wait on an unfinished batch sets job.cancelGPU and calls requiredControl->requestCancel before executor->join. This includes advance(): due publication, finish(): save/finish, reset(): configuration/teardown. The creation handshake at148–152 forwards an earlier owner cancellation to a later-created control, so cancellation can predate device submission. Fixed simulation publication tick remains unchanged regardless of CPU/GPU completion speed. ComputeExecutor.h:718–745: finished is locked completed/total; join waits or executes according to owner policy. Worker completion can race the finished check; this is not evidence of a data race.
2. GradientPipeline.h:330–343: advance increments tick, then joins all jobs due <=tick. reserve/prepare: due=tick+delay, executorDue derived from logical deadline callback; this is NOT an OpenCLRequiredControl monotonic deadline.
3. PRODUCTION HAS NO setDeadlineNs caller. rg finds only the header and OpenCLRequiredControlTest.cpp. deadline defaults0. Thus the shipping cancellation predicate in these games is explicit requestCancel; the phrase 'expired wall deadline' is misleading. A fixed tick publication reaching an unfinished batch can request explicit cancellation. A future prototype setting a monotonic deadline would be a separate path.
4. OpenCLGradient.cpp:802–818: await Flushes then checks required->canceled BEFORE querying the transfer event. read/write:820–846 check cancellation before enqueue, retain an asynchronous event, then await. computeBatch:1043 checks cancellation between dispatch rounds; fill/kernel commands mark enqueueUnobserved. Final cancellation check before commit can decline the result even if computation finished.
5. RequiredCanceled catch:1200–1203 increments requiredCancellations; if proof.needsProof calls protectFailedTransaction. At1222–1230 terminalProof is ONE existing nonblocking query. No event or !canPollEvent returns false. A query API error OR event state != CL_COMPLETE(0), including ordinary QUEUED/SUBMITTED/RUNNING, returns false. No positive coverage does NOT necessarily mean a driver failure.
6. protectFailedTransaction sets shared.failed=true and readyPlans=0, increments proofFailure/quarantine, retains owned endpoints/transaction in the lifetime quarantine. It does not set status.error or session.failed. This is an explicit safe recovery policy that converts an unproven outstanding cancellation to a process-lifetime GPU disable. Empty error is EXPECTED on this path.
7. OpenCLTransferProof.h: commands following a retained event set afterEvent; an old completed event is then insufficient proof. Ambiguous failed enqueue also cannot be proven by polling that event. Retained owned staging/control/input/buffer lifetimes must remain protected. A negative event status and a normal pending event are distinct even though terminalProof currently returns false for both.
8. Reaper OpenCLGradient.cpp:1316–1323 eventually retries terminalProof and clears expired lanes; it does not reset failed or plans. snapshot:733–760 reports available = stored available && !failed. initializationState=2 proves initialization completed, not continuing device availability. A pending=false final snapshot proves quarantine retired, not backend recovery. Device probed/initialization state prevents transparently rerunning initialization.
9. GradientDeviceService.cpp:166–168 classifies canceled control as Cancellation, session.failed as DriverFailure, otherwise BackendDecline. Because quarantine sets global device.failed rather than session.failed, driverFailures=0 / failedSession=0 may coexist with global disable. CPU unavailable selections after failure are consistent with this mechanism. coordinator started/ready reports initialization/service admission state and is not a continuing-health guarantee.

Pacing and observer effect
Settings.cpp:430–439 and Settings.h:106 normal local graphical preset is30ticks/sec. EngineRun.cpp:535–539 returns0 pacing delay for local headless;1179 advances time budget only for graphical/turn sessions. GUI opens read boundary before its pacing wait at1181–1188, allowing worker/coordinator work during idle time. Headless CLI Headless.cpp:506–540 calls stepSession/drawSession in a tight benchmark loop or engine.run without pacing. At identical tick-delay depth, uncapped headless offers far less wall-clock time before publication than normal graphical play. This plausibly increases explicit publication cancellations. It does not prove the GPU would benefit normal graphical play (GPU default differs, device work and renderer contend, wall budget changed).
Instrumented native auto committed4165 vs end-only auto5 or527 is a real scheduling sensitivity, but those runs do not isolate pacing from altered diagnostic workload, CPU affinity, seed, host/GPU concurrency or timing. Instrumentation can give the coordinator extra wall time simply by slowing owner simulation; collecting telemetry can therefore change whether quarantine is reached. Existing end-only emission is after game ticks and cannot slow earlier ticks substantially; its code/build and source should still be matched in repeated comparisons.

What is established vs not
Established: all sixteen snapshots are disabled after an actual quarantine; GPU work was dispatched in all, committed zero in some; one quarantine is sufficient to zero the plan and permanently veto device admission; proof failures are generic nonpositive proof outcomes; explicit cancellation and missing positive proof CAN produce exactly the observed empty-error state; no production monotonic deadline is set.
Not established: first cancellation came from publication rather than save/finish/reset/service shutdown; whether first terminal event was pending, negative, unqueryable, absent, or not covering newer commands; actual driver execution failure; exact quarantine tick; kernel latency versus coordinator CPU starvation; how much diagnostic pacing accounts for field count variation; sustained GPU profit under30TPS graphical rendering.

Safe experiments for root-owned queue (all diagnostic, same initial map/seed/orders and full GCS comparison)
A. First-failure stamp below, same binary with diagnostics disabled/enabled; pair2seeds and N4/auto on both maps. Keep lifetime/proof checks untouched. A 'pending event status + successful query + explicit cancel observed' would directly distinguish normal outstanding work from API failure at that instant. Negative event status/API return documents driver/runtime failure, but still needs why it occurred.
B. Minimal headless pacing-only diagnostic clone: owner sleeps until fixed per-tick monotonic target at1/30s; retain logical deadlines, gradient delay, snapshots and all gameplay. Compare unpaced, small wall budget (~1ms/tick),33.333ms/tick with GPUon and GPUoff. Match checksums; exclude paced wall seconds/TPS from performance claims. Changes in first quarantine/committed work test available wall budget, not ordinary GUI/render contention. Root should ensure pacing placement actually opens the same read phase before sleeping rather than delaying submission.
C. Coordinator scheduling test: identify DeviceBroker thread TID via /proc task comm/source naming, pin only that thread to a free physical core and exclude that core from worker/owner mask; preserve total participant count and record affinity and thread CPU/schedstat/delay. Compare equal host allocation with coordinator isolated vs shared. This changes scheduling resources and is a diagnostic, not a direct six-CPU primary comparison. Do not pin coordinator atop an Oazis/game core. Event completion lag with little coordinator CPU suggests starvation; busy GPU with no CPU delay suggests device work. /proc schedstat deltas require interval alignment and are not device timing.
D. Device contention control: on otherwise identical runs use the alternate physical GPU with GLOB2_OPENCL_DEVICE, record actual UUID/index, GPU compute processes/utilization/memory/power before/during/after. Foreground GPU may currently share NVIDIA device0 with four background games or desktop use; CPU-disjoint workloads still share GPU/cache/memory/power. Driver context creation latency versus steady kernel delay should be separated. Compare quiet-device repeat only when parent explicitly schedules it.
E. Existing conservative checkInterval/poll knobs, if exposed in a prototype, can test polling response vs GPU progress, but never add Finish, blocking cancellation, or relax proof. Change one at a time; record observed event status and CPU cost. More frequent queries can change timing and power; a retry observing completion is not permission to release endpoints without the existing proof.
F. Controlled required-control harness can replay cancellation before enqueue, during write, after fire-and-forget kernels before covered read, during convergence read, during final read, after positive proof. Mock event states {pending,complete,negative,error}, keep CPU recovery and lifetime-oracle assertions. This establishes state transitions without relying on flaky driver timing; real run stamps establish which case occurred. No blind reset of failed/readyPlans, and no feature deletion.

Minimal instrumentation proposal (NO edits/builds yet)
Only OpenCLGradient.cpp TU: bounded fixed-size diagnostic ring, env opt-in, allocated statically or bounded before any device work; one record per transition until first quarantine, no print/file IO on hot path. Capture monotonic ns + thread CPU ns, transaction/control identity, field count/size/family, stage enum {costPrepare,writeInitial,writeCosts,writeDescriptors,dispatch,changedRead,finalRead,commit}; enqueue result, event-present, needsProof, canPollEvent, cancellation predicate at preenqueue/await/dispatch/commit. Wrap the EXISTING terminalProof query to record its exact API return and execution-status integer; preserve number/order of queries and all branches. Record first observed cancellation and last successful query, dispatch round, last covered enqueue/event. Store query-skipped reason {noEvent,notCovering,diagnosticInjection}, quarantine ns and successful reaping ns. Emit only after first failure / via separate artifact file at safe end; emitting on first failure after the decision changes subsequent CPU fallback timing, so its timing record remains diagnostic.
No new gradient/control header fields required to distinguish pending/error/proof: needsProof and canPollEvent are public. OpenCLRequiredControl private canceled/deadline cannot be inspected from this TU; current production has no deadline setter so explicit request is inferred, not directly stamped. To prove owner publication/save/reset origin, a second tiny patch in a .cpp caller that drains a pipeline can timestamp root-level contexts, but direct inline wait instrumentation in GradientPipeline.h would rebuild many TUs. Alternative explicitly state the limitation and correlate first cancellation with existing per-tick diagnostics, whose observer effect must be reported. Do not invent a cancellation timestamp from the time the coordinator first notices it; that is only an observation timestamp. An external perf/uprobe trace of requestCancel is unreliable when inlined/stripped.
A singleton ring shared coordinator/reaper needs safe atomics or thread-local lane buffers plus synchronized end snapshot; do not introduce telemetry data races. The first failed transaction is enough to test this hypothesis; avoid unbounded verbose tracing. Compare instrumented code diagnostic opt-off/on to measure whether the observer changes committed counts, and never pool diagnostic timings with benchmark means.
