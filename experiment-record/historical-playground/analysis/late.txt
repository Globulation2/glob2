Highest-priority explanatory lead: pool sizing and wake churn
Confirmed source/configuration facts:
- Before #961, src/ai/AIThreading.h defaultAIThreadCount counted AI controllers and returned clamp(min(controllers, hardware_concurrency),1,4), owner included. Eight Nicowars therefore use four participants (three workers) on this32-logical-CPU host.
- Oct8 #961 / b5c9f3ed2 replaces it with src/common/ComputeThreads.h: default native compute participants equals std::thread::hardware_concurrency(), fallback1. No Linux sched_getaffinity/cgroup availability lookup. Browser-only cap8 is added later by #1094; native remains uncapped.
- Engine::beginSession calls configureCompute(resolveComputeThreadCount(globalContainer->computeThreads)); default requested value0 means auto. Historical runner sends no explicit --compute-threads option. Its taskset gives each process6 CPUs, which limits execution eligibility, not the reported hardware concurrency used by this code.
- Therefore expected native pool is32 participants/31 worker threads inside each6-CPU group after #961, versus four participants previously. This is a source-derived expected count; these benchmark runs did not retain /proc thread inventories or explicit resolved-count telemetry, so actual runtime count was not directly sampled here.
- Map::configureCompute also resizes periodic and synchronous gradient workspaces to compute.threadCount(). More participants can retain more solver/cache scratch, in addition to stacks and scheduler objects.
- ComputeExecutor ready condition variable uses notify_all on deferred submissions and lane completion; all workers reacquire the same mutex and inspect claimability. Oct8 source already has this behavior. GPU support adds external completion/continuation wakeups after Oct8.
- Root observed a final run with CPU127.56s versus wall44s, including system CPU53.2s. Large systemCPU is consistent with futex/scheduler churn under oversubscription, but not proof without sampled stacks/perf/strace.
Historical evidence:
- #961 measured matching explicit counts approximately unchanged; auto8 vs4 cost18–22% extra CPU and3–6% longer wall on five-repetition short windows. macOS-only; not this x86 host,32 participants, full Nicowar games or final integrated workload. No speedup claim.
- #944 intentionally makes owner wait for deferred work whenever any worker exists. Its quiet Oazis11-Maxima18048-tick experiment: one worker wall1.35x/CPU0.98x baseline;2workers0.84/0.95;3workers0.72/0.96;4workers0.70/0.97;8workers0.73/1.03. Beyond3–4 workers gains plateau in that workload; extrapolation to31 workers is unsupported.
Interpretation: #961 is a strong candidate for a material part of Oct5->8 CPU/systemCPU increase. It cannot explain how much until explicit-count ablation. User's six dedicated virtual CPUs do not currently imply six actual engine participants. The experiment measures default historical configuration evolving over time, not equal internal worker counts.

Highest-priority RSS lead after Oct8: headless GPU default
Confirmed:
- Oct10 #1045 /0661f9605 adds explicit GPU switch. Settings::gpuComputeEnabled(bool headless) returns saved optional choice or headless. Fresh profile + headless =>GPU on; graphical default off. --gpu on/off and compatibility GLOB2_GRADIENT_BACKEND environment override.
- GlobalContainer::configureGradientBackend chooses OpenCL. Map::configureCompute sets external backend initialization and starts GradientDeviceService when threads>=2/backendOpenCL. Service delegates initialization to its asynchronous broker and supports exactCPU fallback.
- #1045 dynamically loads installed OpenCL driver; implementation describes bounded engine storage64MiB host/128MiB device. Driver/context allocations are separate and may enlarge processRSS. Device allocation itself is not processRSS.
- Fresh benchmark profiles contain no gpuCompute entry; runner passes no GPU flag. Logs lack GPU execution counters. Hence requestedGPU-on is established; actual dispatch/device initialization success is not measured in this cohort.
- GLOB2_GRADIENT_DIAGNOSTICS=1 enables service diagnostics, while structured headless reports gradient/device counters. Use a diagnostic reproduction to establish requested/available/executed status; do not infer dispatch from readiness alone.
Historical evidence:
- #1045's final merge explicitly makes no new performance campaign claim. Earlier67-generator512² fixed windows with eight slots showed forcedCPU vs master warmCPU+1.20%, wholeCPU+1.06%, runtime-0.48%; forcedOpenCL warmCPU-11.63%, wholeCPU-9.46%, runtime+5.92%, p99+9.74%. Interpretation: GPU service/driver init is a highly plausible explanation for a substantial Oct8->11RSS increase with almost flat TPS/CPU. Four parallel latest games may additionally share/contend on the sameGPU; CPU affinity does not partitionGPU access. GPU-off ablation is first priority.

User constraint: preserve all new features
The ablations above are diagnostic experiments, not shipping recommendations to remove features. The optimization candidates that preserve behavior are:
1. Resolve automatic native compute size from CPUs actually available to the process, then cap or tune useful parallelism. Preserve explicit overrides and deterministic deadlines. On Linux use sched_getaffinity (and consider cgroup CPU quota); equivalent platform discovery needs portability coverage. Four versus six participants is an empirical choice, not a guarantee.
2. Reduce broadcast wakeups with bounded worker activation or targeted notifications, retaining per-lane dependency and deadline ordering. notify_one replacement everywhere is unsafe: one job can unlock several lanes, and GPU continuations can arrive asynchronously. Benchmark futex/context-switch counts and require exact checksums before claiming savings.
3. Make headless GPU preparation lazy until an eligible request exists, or size admission by workload. Keep GPU compute available and exact CPU fallback. Separate driver startup RSS from retained per-field host allocations. Avoid disabling GPU as the proposed product fix.
4. Preserve building scheduling and resource snapshots while limiting speculative work and reusing scratch buffers. Reader-demand policy and immutable lease lifetimes provide useful optimization boundaries. Do not remove owner RNG streams, catalogs, delayed growth or area effects.
5. Investigate allocation/retention by component before changing snapshot/cargo/catalog representation. GPU-off/count controls locate the cost; they do not establish that features should be removed.
