Recommendation

Accept bounded wakeups, keeping the existing shared priority scheduler, job eligibility, ordering and ownership model. This is the simplest efficient design supported by the tested workloads. It is not a claim of a universal optimum. The production change only limits deferred-submit notifications to the already computed runnable count, broadcasting when runnable work can occupy the whole worker pool. It adds no queues, clocks, estimates or scheduling state.

What changed and why it helps

Previously a submission with several runnable jobs woke the entire pool. Most awakened workers could find no work, contend to inspect the scheduler, and sleep again. The candidate reduces those opportunities. The lock is not held while AI callbacks execute: different AIs still run concurrently, and each AI retains its sequential authoring and ordering rules. Large declines in system CPU and voluntary context switches support the wakeup-overhead explanation. These counters do not assign every saved cycle to a particular futex or prove that all remaining coordination costs are solved.

The decisive comparison

The final campaign ran 256 whole games: baseline and treatment for 32 fixed seeds on each of two maps, in two regimes. Every run reached a winner; all 128 matched pairs had matching endpoints. Playground is 128×128 with eight Nicowars; original Oazis is 256×256 with eleven. Baseline-first and treatment-first orders were balanced. The single-game regime used the available 32 logical CPUs and auto resolved 32 participants. The concurrent regime ran four games, each with six participants confined to three physical cores and their six SMT threads. These regimes change allocation and concurrency together and cannot determine a universal worker count.

Single-game interpretation

Playground mean end-to-end time fell 35.5243→31.5036 seconds (−11.32%; paired 95% interval −11.65% to −11.03%). Total CPU fell 161.6468→97.1527 seconds (−39.90%; −41.30% to −38.89%). Inner simulation TPS rose 1511.98→1711.54 (+13.20%). Oazis time fell 182.0584→176.7442 seconds (−2.92%; −3.22% to −2.57%); CPU fell 731.4527→604.4154 seconds (−17.37%; −17.82% to −16.89%). Larger useful work on Oazis dilutes the relative coordination savings. System CPU fell 83.94% and 78.00%, respectively; voluntary context switches fell 78.66% and 74.27%. Peak RSS was effectively unchanged, apart from about 0.8 MiB lower on Playground.

Concurrent throughput interpretation

Playground completed-games throughput changed +0.83%, with an eight-wave paired 95% interval −1.48% to +3.28%. Oazis changed −0.61%, interval −1.89% to +0.61%. Neither establishes a throughput gain or loss. CPU per game changed −1.17% and −0.34%, respectively. Do not extrapolate the single-game CPU savings to the six-participant tournament configuration. Four games sharing a wave are clustered, not four independent host measurements.

Why the alternatives were rejected

Static round robin first failed a presentation contract; its unsafe modes are not qualified. Strict lane placement can strand idle workers when independent runnable heads collide. Distributed FIFO queues and local completion reduced some synthetic overhead, but lost important urgency behavior and generally trailed the small wake-only change in native games. A required urgent job waited roughly 13–15 ms behind a backlog versus about 0.34 ms in the baseline diagnostic. Priority-aware queue variants repaired much of that synthetic latency, but did not establish a native-game gain sufficient to justify the extra machinery. These diagnostic delays are not measured input latency.

Duration estimates and granularity

Fixed hints, last duration and smoothed duration estimates were compared with clock-only, observe-only, bare-steal and weighted-with-stealing controls. Experiments accounted for active as well as queued CPU work, consistent time units, cold starts, drifting costs and wrong predictions. Last-duration and smoothed placement were each faster than observe-only in only 7 of 24 heterogeneous micro cells; their median wall changes were approximately +3.35% and +6.23%. These are descriptive synthetic-cell summaries, not population game estimates. Estimates were not promoted into production. Immediate-counter removal had no demonstrated native hot-path benefit. Near-full wake heuristics remain deferred: a balanced four-participant screen did not reproduce the earlier apparent loss or establish a gain.

Evidence quality and corrections

The retained inventory covers 1,944 timing observations, not 1,944 independent games. The final campaign has 64 seed-map combinations reused across treatment and regimes. Earlier native pilots and an additional 120 confirmations always ran baseline first; their order confound is retained prominently and they are not pooled with the final counterbalanced campaign. Mature-save and small-map screens have limited independent states. The final 256 raw results were independently audited and their canonical estimators reproduced from this actual bundle using only the Python standard library. Canonical bootstrap intervals use 10,000 draws and floor-index quantiles; independent alternative RNG/quantile sensitivity calculations are separately labelled.

Correctness and integration

The earlier exact-header qualification includes 40 per-tick traces across 20 paired contexts, small and large maps, mixed AIs, mature states, load continuations, and actual OpenCL runs. This is separate from final-game endpoint equality. Final release integration at efb843d8047bba6f546c031614a31c917513ad54 against 054804590ee1dd109f09642fc05654c324f08344 passed 56 native unit cases, two save/load engine cases, an 843-row golden trace, and a verbose 54-assertion partial-wakeup case with four real workers. Direct Chromium and Firefox engine corpora each passed 228 cases and 8,117,508 assertions; both exported matching 843-row traces and passed actual four-worker partial-wakeup probes. Known limits

Chromium UI/lifecycle passed. The Firefox UI wrapper failed at a software-canvas startup call, and an original-executor-header control reproduced the same failure. That UI test remains failed. Candidate source and all 7,690 served runtime files were hash-restored; control-derived object directories were quarantined so future builds must recreate them. Windows, macOS, Android and iOS candidate runtime, another physical CPU/GPU vendor, manual native play, quantitative frame pacing, input latency and sustained battery/thermal behavior are unverified. CPU winner timings do not establish GPU performance. No engine feature, resource profile, universal pool size, save format or simulation version changes are included.

Specific next experiments

First profile the remaining scheduler lock, scans and wakeups in mature games after bounded wakeups; use instrumented runs separately from ordinary timings. Only build a priority-preserving ready index if remaining scans dominate. Separately vary CPU allocation, participants and concurrent-game count on multiple devices, preserving resource policies rather than encoding this machine’s optimum. Test a near-full broadcast crossover only with counterbalanced independent games. Investigate owner help or larger useful task chunks only if measured stalls or fine-grained scheduling remain important, retaining GPU/presentation context restrictions. For broader engine gains, prioritize proven duplicate field or snapshot work and exact invalidation/ownership boundaries, then GPU transfer/batching economics. Every candidate still needs per-tick parity, save/replay continuity and representative workload validation.
