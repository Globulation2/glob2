# Unit view request frequency

Release build of the draft PR plus diagnostic tick request counters. Same two-layer layout, no policy adoption. Six real AI initial states from the earlier agreement corpus, each to tick 12,000, movement shadow K=1, participants=2. Two sustainable fixtures with Null AI run headless for 1,024 ticks, each with shadow K=1 on/off. Six actual concurrent Engine GUI sessions run 32 warmup + 512 measured ticks at normal game speed (30 TPS), software/Xvfb at 640x480, presentation target 60 FPS, participants=2: ordinary/1,024-unit/Cortex colonies, selected unit on/off. Frequency totals include the whole loaded session (including warmup and initial observation), not just timing windows. These are exact request counts for each session, not performance comparisons. GUI presentation admission depends on pacing and preparation readiness; its frequencies can vary with host load. Concurrent tournament load is recorded, not treated as clean FPS/TPS evidence.

The denominator is distinct logical tick numbers seen by the snapshot store. Same-tick requests OR their normalized masks; upgrades reclassify the existing tick. Paused repeats and invalidations cannot multiply it. Details imply cores. Report core-only, core+detail and neither as exclusive categories, and compare observed tick range with engine advances. Actual core/detail capture counts and authoritative bytes are separate from requests, copied record metadata, sidecars or retained capacity. GUI selection configurations are controlled cases, not estimates of human selection frequency. AI requirement attribution is checked against actual controller declarations and broader full-observation queries.

Commands, fixture identities and all logs/results are retained per case. No timing or FPS benefit is inferred from these counts. Supported platform sample: Linux x86-64 only. No human multiplayer, macOS, Windows, browser or GPU rendering coverage.
